# 卡:限速安全扫描(别把靶场打挂 —— 打挂即丢分)

**适用**:任何**开始高强度扫描/爆破**之前;以及目标突然变慢、超时、整站 5xx 时。

> 教训来源:公开同题轨迹里出现过"300 路径并发扫描把 php-fpm 打满 → 容器 OOM(512MB)→ 整题不可用"。
> 这不是目标坏了,是我们自己把题打死了。

## 0. 扫前基线(10 秒,必须做)
```bash
for i in 1 2 3 4 5; do curl -sk -o /dev/null -w '%{time_total}\n' "http://T/"; sleep 0.3; done
```
记下正常延迟;之后任何扫描期间**定期复测**同一路径,延迟涨 3 倍或出现 000/5xx 就是过载信号。

## 1. 并发与速率
- 目录/参数扫描:**并发 ≤10**,单目标优先 5;
  `ffuf -t 5 -rate 20`、`dirsearch --threads 5`、`gobuster -t 5`。
- 凭据攻击:**串行** + 按限速窗口(见 credential-wall:先 5 发量安全速率)。
- 长跑一律后台:`python3 /app/tools/job.py start "ffuf ..." --name dir1`,不要在前台等。

## 2. 已知会打死目标的模式
| 模式 | 后果 | 替代 |
|---|---|---|
| 并发 100+ 的目录爆破 | php-fpm worker 占满 → OOM/502 | 并发 ≤10,分批,先小字典 |
| 大量慢请求(每个挂 5~10s) | worker 被占死 | 加 `-m 5` 超时,失败即跳过 |
| 对登录口并发撞库 | 设备/应用熔断或封 IP | 串行 + 延时 + 限次 |
| `-p-` 全端口 nmap | 设备连接表打满 | `-p 1-10000 --min-rate 500` |

## 3. 过载后的处置(别继续加压)
1. **立刻停掉所有 job**:`python3 /app/tools/job.py list` → `stop <name>`;
2. 等 30~60 秒,单请求探测恢复(`curl -m 5 -o /dev/null -w '%{http_code}'`);
3. 恢复后**降一档**再继续(并发减半、字典换小);
4. 把"目标对并发敏感"写进黑板(队友别重复踩)。
5. 长时间不恢复:换攻击面(证书、SSH、别的端口),别在同一入口上空转。

## 4. 判据
- `000` / 连接重置 / 5xx 连续出现 = 过载或被打挂;
- 不是"题坏了",也不是"我该重试更快";
- 记录:什么速率、多少并发、跑了多久导致的 —— 下一轮直接按安全档位开局。
